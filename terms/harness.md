term: Harness
zh: 韁繩
oneline: 模型只負責產生文字，其餘全部是外面那一層在做。

## 定義

Harness 是包在模型外面的那一整層程式。

模型自己只做一件事：讀進一段文字，吐出一段文字。它不會查資料庫、不記得上一輪發生什麼、也不知道任務到底完成了沒有。這些全部是 harness 在做：

```flow
組上下文 | 這一輪要餵進去的東西：任務、前幾輪結果、可用的工具清單
接住輸出 | 看模型吐出來的文字裡有沒有[[tool-use|工具呼叫]]的格式
實際執行 | 真的去查、去寫、去送出
回填結果 | 把執行結果變成下一輪的輸入
判斷收工 | 還沒完成就再跑一輪，跑太多輪就停下來
```

英文 harness 原意是套在馬身上的整套挽具——韁繩只是其中一條。分工也剛好一樣：**馬提供力量，挽具決定這股力量接到哪台車、往哪個方向。**

所以「harness engineering」講的是把工夫從調模型，移到調外面這一層。

## 為何會出現

以前模型是主要變因，換一個更強的模型，什麼都會變好。現在前段班的模型能力已經接近，**同一個模型包在不同的 harness 裡，差距常常比換模型還大。**

差在哪？工具描述寫得含糊，它就挑錯工具；[[context-window|上下文]]塞滿雜訊，真正重要的那句被埋掉；[[agent-loop|迴圈]]沒有停止條件，它就在原地鬼打牆。這幾件事換模型都不會好。

跟[[guardrail|護欄]]很容易搞混，但兩者管的層次不同：

| | 管什麼 |
|---|---|
| Harness | 它**怎麼運作**——看得到什麼、做得到什麼、能試幾次 |
| 護欄 | 它**不准做什麼**——工具清單、權限範圍、[[egress\|出向管控]] |

護欄是裝在 harness 上的。==沒有 harness，就沒有地方裝護欄。==[[agent-governance|代理治理]]再往上一層，是把這些機制加上紀錄一起管的制度。

## 金融背景怎麼理解

兩個能力差不多的理專，一個手上有整合好的客戶系統、有現成的商品比較表、有覆核流程接著；另一個每件事都要自己翻。半年後產出差一大截——**差的不是人。**

這件事在導入時最常被跳過。開會問的第一句常常是「我們要用哪一家的模型」，但實際決定成敗的是下面這幾題：

| 實際上會問的問題 | 其實在問 harness 的哪一塊 |
|---|---|
| 它查得到哪些資料？ | 工具怎麼定義、開了什麼權限 |
| 它記不記得上一步做了什麼？ | 上下文怎麼組進去的 |
| 它會不會一直重複做同一件事？ | 迴圈的停止條件 |
| 出錯之後查不查得到？ | 每一輪的紀錄留在哪 |

> [!提醒] 換更強的模型，補不了 harness 的洞
> 如果它現在會挑錯工具、會忘記任務目標、會鬼打牆，那多半不是模型不夠聰明，是外面那層沒寫好。==同一組問題換一個模型，通常只會換一種出錯方式。==

實務上的意涵：這一層是**我們自己的工程資產**，不是廠商給的。模型會一直換，但工具怎麼定義、紀錄留成什麼樣子、哪一步要停下來讓人確認，這些留得下來。
